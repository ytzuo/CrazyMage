# 失控法师性能保障指南

供本项目后续编码和审查参考，适用于当前 TypeScript + Phaser 3 + Vite 框架，以及后续升级、危险法术和 Boss 的实现。当前已加入追击怪、火球伤害、生命值和死亡重开；完整一局及高负载战斗性能尚未验证。当前功能与验收条件见 [需求说明](requirements.md)。

## 1. 目标与证据

性能保障需要同时关注首次进入、持续战斗、暂停和反复开局。先确认慢在哪个阶段，再选择优化方式。

| 方面 | 后续目标 / 检查要求 | 测量方式 |
| --- | --- | --- |
| 首次进入 | 记录冷启动、缓存后启动到可操作的时间；先建立基线，再确定目标 | 从导航开始到画布出现且输入生效，结合网络与浏览器 Performance 记录 |
| 持续战斗 | 以 60 FPS 为初步目标，整帧时间预算约 16.7 ms；支持时也观察高刷新率表现 | 帧间隔分布、慢帧数量、浏览器时间线；不能只看平均 FPS |
| 暂停 / 失焦 | 游戏循环停止，战斗时间、冷却和弹丸冻结，继续后不补发积压攻击 | 检查循环状态和恢复后的实际行为 |
| 重开 / 切换场景 | 对象、监听器、定时器不随重开次数持续增长 | 多次重开后的对象计数与内存快照，考虑正常缓存和垃圾回收时机 |
| 窗口适配 | 全屏布局正常，尺寸不变不重建画布；大窗口和手机尺寸不会引入明显卡顿 | 检查 CSS 尺寸、实际画布像素、DPR 和缩放操作 |

这些是检查目标，不是已经通过的设备性能承诺。新增战斗系统后需要重新建立对应基线。

当前可用的历史证据见 [启动卡顿检查](performance.md)：1280 × 720 视窗、启动后 120 帧的一次采样，平均渲染 CPU 耗时 0.34 ms，95% 分位帧间隔 8.90 ms。它不包含下载、解析、完整更新逻辑或 GPU 完成时间；未记录足够的设备信息，不能作为跨设备达标线。

## 2. 静态场景只生成一次

本次已确认的主要问题是 690 块静态地砖保存在 Graphics 绘图命令中，每次渲染仍需处理路径和填充。一个 Graphics 对象不等于一张已经缓存好的图片。

- 地砖继续使用小纹理重复铺设，法阵和重复装饰使用纹理与 Image。避免逐帧重画整张地图。
- 程序绘制纹理在场景准备阶段生成。先检查纹理键是否存在，生成后销毁临时 Graphics；场景重建时复用共享纹理。
- 不把所有内容缓存成一张巨大图片。纹理大小、显存占用和目标设备上限需要单独评估；重复图案优先使用小纹理。
- 少量人物形状、地图边界等简单 Graphics 可以保留。是否进一步缓存由测量决定，避免为了缓存增加复杂度。
- 动态预警、冰环和火区只更新必要的对象。预警出现时创建，结束时回收；不要每帧重建全部对象。
- 留意大面积透明图层、叠加发光、全屏滤镜带来的重复像素绘制。CPU 渲染耗时低但帧率低时，检查 GPU 和实际画布分辨率。

共享纹理由场景或游戏统一管理。销毁单个敌人或特效时，不应顺带销毁其他对象正在使用的纹理。

## 3. 保持逐帧工作可控

逐帧路径包括场景 `update`、实体更新、命中检测和渲染回调。先控制工作量，再考虑局部技巧。

- 避免逐帧生成纹理、重建地图、解析配置、排序全部敌人、操作布局或输出日志。
- HUD 只在内容变化或固定低频时更新。当前小地图复用约每 80 ms 发布一次的位置状态，按怪物 ID 复用 SVG 红点，仅在大致位置变化时更新标记，死亡或重开时移除失效标记，不增加渲染循环。怪物标记数随怪物上限约束；血量和经验显示沿用按需更新的方式。
- 复用明确的临时计算对象，避免在大量实体的每次更新中创建数组和对象。只有出现分配或垃圾回收证据时才进一步引入对象池。
- 运动和冷却基于游戏时间及帧间隔计算，不以“每帧固定移动几像素”实现。暂停期间不累计战斗时间。
- 当前角色更新限制单次 delta 不超过 50 ms，以防恢复时突然跳远。它是异常帧保护，不能通过增大限制或平滑数据掩盖低帧率问题。
- 寻敌、路径选择等逻辑可按适当低频计算，移动和视觉仍每帧更新。更新频率需要兼顾响应速度，不能直接牺牲手感。
- 新增碰撞时估算比较次数：所有弹丸逐个检测所有敌人会随两者数量乘积增长。先用距离平方等简单筛选；出现瓶颈后引入空间分区，并验证边界漏判。

当前火球冷却、寿命和地图边界自然限制了在场数量。加入穿透、多弹丸、连锁闪电等升级后必须重新评估，不能沿用基础火球的负载假设。

## 4. 每种战斗对象有明确生命周期

实现新系统前，在代码或功能说明中写清以下四项：最大同时数量、产生频率、结束条件、回收责任。上限应结合玩法和实测确定，不在缺少证据时随意承诺支持某个怪物数量。

| 对象 | 需要明确的限制 | 必须覆盖的结束路径 |
| --- | --- | --- |
| 敌人 / 精英 | 同屏上限、生成节奏、场外处理规则 | 死亡、结算、重开、场景关闭 |
| 弹丸 / 闪电 | 发射频率、升级后的最大数量、持续时间 | 命中、超时、越界、重开 |
| 火区 / 冰环 / 预警 | 同时存在数量、范围、持续时间 | 消散、攻击取消、结算、重开 |
| 经验和掉落 | 最大数量、合并或回收策略 | 拾取、结算、重开 |
| 特效 / 飘字 / 音效 | 生成频率、并发上限 | 播放结束、重开、场景关闭 |

回收应处理显示对象、数组引用、碰撞关系、Tween、定时事件和订阅。对象池只有在重复创建确实导致瓶颈时采用；复用对象必须重置速度、透明度、计时、命中记录及回调，防止旧状态残留。

验证时至少反复重开 10 次，观察计数是否回到预期范围。一次内存上涨可能来自纹理缓存或垃圾回收延迟；持续增长需要用快照确认引用来源。

## 5. 暂停、输入和窗口生命周期

- 保留当前 `game.pause()` 与 `game.loop.sleep()` 配合使用的行为；继续时恢复游戏并唤醒循环。只跳过 `update` 不能保证停止渲染。
- 窗口失焦和页面隐藏后自动暂停。恢复必须由用户操作触发，不能在后台继续运行战斗。
- 暂停时清空键盘与摇杆状态，避免恢复后角色自行移动或攻击。验证按住 WASD / 方向键时切换窗口的情形。
- 通过游戏时间安排战斗事件；如果确实使用网页定时器，需要明确暂停与取消策略。
- `ResizeObserver` 比较新旧尺寸，只在实际变化时调整画布；避免在观察回调中反复改变触发布局的尺寸。
- 场景关闭、页面组件销毁和开发热更新时，解除监听器、断开观察器、取消自己的异步任务并释放游戏对象。销毁流程也要覆盖循环已休眠的情况。
- 大窗口适配需要检查实际渲染像素和 DPR。是否限制渲染分辨率由清晰度与性能测量共同决定，不直接提高到设备最高像素密度。

最少检查暂停 / 继续 5 次、失焦 / 恢复、按键释放、摇杆拖出区域和窗口缩放。修改尺寸逻辑时覆盖桌面 1280 × 720、手机竖屏 390 × 844、横屏 740 × 390；涉及分辨率策略时补充大窗口和实际设备检查，并恢复临时浏览器尺寸设置。

## 6. 区分启动慢与运行慢

冷启动涉及资源下载、脚本解析、Phaser 初始化、纹理生成和首帧；持续战斗涉及更新、渲染、GPU、内存与其他页面负载。分别采样，不能用首帧后的数据解释首帧前的问题。

- 记录开发服务器还是生产预览、是否有缓存、是否打开开发工具、同时运行的游戏实例数量。
- 首次进入慢时先查看网络和主线程时间线，定位耗时阶段，再处理资源拆分、预加载或初始化工作。
- Phaser 目前单独分包。构建产物大小及大包警告是调查入口，不能直接认定它们导致本次卡顿，也不要仅为消除警告提高阈值。
- 生产体验使用 `npm run build` 后的 `npm run preview` 验证，访问实际启动输出的地址。开发模式诊断和热更新成本需要单独说明。
- 新增图片、音频时明确加载时机和失败处理，避免战斗中临时下载关键资源。可延迟准备的内容，应在不影响当前操作的阶段处理。

## 7. 现有诊断工具的正确用法

实现位于 [`src/game/diagnostics/performance.ts`](../src/game/diagnostics/performance.ts)，由启动代码在开发模式调用。诊断不增加游戏界面文字。

开发工具控制台可读取：

```js
const canvas = document.querySelector('#game canvas');
JSON.parse(canvas?.dataset.performance || 'null');
canvas?.dataset.loopRunning;
```

`data-performance` 在首个渲染帧开始采样，达到 120 帧，或累计墙钟时间达到 4 秒后的下一次渲染结束时写入。不是 4 秒硬超时；暂停会停止渲染，因此结果也可能延迟出现。暂停会重置帧间隔起点，避免将暂停时长计入下一帧间隔。

| 字段 | 含义与限制 |
| --- | --- |
| `background` / `viewport` / `frames` | 场景标记、游戏逻辑尺寸和实际采样帧数；没有记录设备、DPR 或缓存状态，需要另行补充 |
| `meanRenderMs` | PRE_RENDER 到 POST_RENDER 的平均 CPU 耗时，不包括此前的场景更新，也不是 GPU 完成耗时 |
| `first20RenderMs` | 最多前 20 个渲染样本的平均 CPU 耗时；不足 20 帧时使用已有样本 |
| `meanFrameMs` / `p95FrameMs` | 渲染帧起点之间的间隔；受刷新率、调度、页面负载影响，不等于渲染函数耗时 |
| `data-loop-running` | 开发模式下暂停 / 恢复时记录的循环状态；暂停应为 `false`，继续应为 `true` |

没有结果或帧数很少时，先确认页面是否暂停。现有工具只用于启动后的短时观察；持续战斗、内存或 GPU 分析需要另行录制，不能据此宣称整局稳定。

## 8. 修改后的验证流程

1. **确定影响范围。** 文档修改只检查内容和链接。游戏代码修改运行 `npm run typecheck` 和 `npm run build`，再验证受影响的操作。
2. **性能相关修改先采集基线。** 使用同一设备、浏览器、窗口、DPR、构建模式和操作路径。只保留一个参与测试的游戏实例；记录冷启动与缓存后启动的区别。
3. **至少各采样 3 次。** 修改前后分别记录启动、正常移动与连续攻击；新增战斗系统后补充预计最大敌人数、法术组合和危险效果同时出现的场景。比较中位数及慢帧分布，保留原始结果。
4. **检查明显回退。** 同条件下耗时反复增加超过 20%，或反复出现影响操作的停顿时，调查原因。20% 是调查触发值，不是统一发布门槛；极小耗时的相对变化要结合绝对值判断。
5. **检查生命周期。** 按第 4、5 节验证重开、暂停、失焦和尺寸变化。涉及持续生成或资源回收的修改，进行至少 3 分钟运行观察；完整战斗版发布前覆盖一局 6–8 分钟及结算重开。
6. **报告实测与缺口。** 类型检查和构建通过不能证明性能达标。未测试手机、GPU 或整局时，明确说明；没有新改动或新疑点时不重复扩大检查范围。

性能测试仍需验证玩法：移动和瞄准独立、斜向速度一致、火球冷却正确、暂停冻结、恢复不跳跃、危险升级预警清晰。降低卡顿不能破坏这些行为。

## 9. 性能问题记录模板

每次确认或解决明显卡顿时，在 `docs/` 留下简短记录，包含：

- 现象：首次进入、持续战斗、暂停恢复还是重开后出现；复现步骤。
- 环境：版本、设备、浏览器、视窗、DPR、开发 / 生产、缓存情况和并行实例。
- 已确认原因：代码路径、时间线或资源证据；把未验证的假设另列。
- 修改前后：原始样本、采样次数、平均与慢帧指标、对象或内存变化。
- 处理方式：具体改变、保留的玩法规则、对应文件。
- 验证：实际执行的检查、结果、仍未覆盖的设备或阶段。

未取得可比的修改前数据时，只报告修改后观察，不写提升百分比或倍数。当前历史记录可参考 [启动卡顿检查](performance.md)。

## 10. 提交前简查

- [ ] 静态纹理没有放进逐帧生成路径，逐帧 DOM / 日志受控。
- [ ] 新对象有数量、寿命和回收责任，重开清理完整。
- [ ] 暂停与失焦停止循环，继续后的输入和计时正确。
- [ ] 涉及窗口的改动没有重复 resize 或意外提高渲染像素。
- [ ] 检查范围与改动匹配；性能结论有可比证据且标明局限。
- [ ] 生产界面保持全屏、无介绍，诊断数据只在开发模式提供。
